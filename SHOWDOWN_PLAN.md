# Showdown Build Plan

## Summary

Showdown is an infinite, blind, head-to-head voting mode for jokes. A signed-in user sees two jokes and chooses the funnier one without being told whether either joke was written by a human or generated by AI.

The first release is for text jokes only. The data model and voting system should remain usable for image memes later.

## Product decisions

### Source classification

Showdown has exactly two competitive source categories:

- `human`: a human submitted the final wording or edited an AI draft before publishing it.
- `ai`: the model output was published without the human editing its wording.

An AI joke does not count as human-authored merely because a person wrote the prompt or selected it for publication. Conversely, once a person edits the generated joke and publishes the edited result, the joke is linked to that human and competes as human work.

This rule is necessarily partly honor-based. The application can record how content moved through its own editor, but it cannot reliably detect whether text pasted into the normal submission form originated in an external AI tool.

If editable generated drafts are added later, preserve their lineage in a separate nullable field such as `edited_from_generation_id`. This field is for internal analytics and does not create a third competitive source category.

### Initial game rules

- Only authenticated users with complete profiles may play.
- Only `kind = 'text'` jokes are eligible.
- The two choices are displayed as A and B with equal visual weight.
- Author, source, prompt, model, ratings, and existing Showdown statistics are hidden before the vote.
- A user cannot be shown their own joke.
- A joke cannot compete against itself.
- Left and right placement is randomized.
- Prefer jokes in the same category so comparisons are reasonably fair.
- Avoid jokes and pairs the voter has seen recently.
- After the vote, reveal whether each joke was human or AI, then load the next pair.
- Human-vs-human, AI-vs-AI, and human-vs-AI votes all affect the joke leaderboard.
- Only jokes classified as human contribute to human-writer leaderboards.

## Success criteria

The MVP is successful when:

- A signed-in user can vote through an effectively endless sequence of valid pairs.
- A vote can be recorded no more than once for a server-issued match.
- No hidden provenance is included in the pre-vote Showdown response.
- New and under-exposed jokes receive opportunities to compete.
- The joke leaderboard is resistant to tiny sample sizes.
- AI-generated jokes never credit the prompting user as a human joke writer.
- Match history is retained so ranking formulas can be rebuilt or changed later.

## Data model

Create a new idempotent migration, expected to be `supabase/migrations/0009_showdown.sql`.

### `showdown_matches`

One row represents one pair issued to one voter. It also acts as the authorization token for the eventual vote.

Suggested columns:

| Column | Purpose |
| --- | --- |
| `id` | Match identifier returned to the client. |
| `voter_id` | Profile that received the pair. |
| `left_joke_id` | Joke displayed on the left or first. |
| `right_joke_id` | Joke displayed on the right or second. |
| `winner_joke_id` | Chosen joke; `NULL` until the match is completed. |
| `created_at` | When the pair was issued. |
| `voted_at` | When the vote was accepted; `NULL` for an abandoned match. |

Database invariants:

- `left_joke_id <> right_joke_id`.
- `winner_joke_id` is `NULL`, `left_joke_id`, or `right_joke_id`.
- All joke references use foreign keys.
- The winner and vote timestamp transition together.
- A completed match cannot be changed.
- Only the assigned voter can read the match through the authenticated client.
- Direct client inserts and arbitrary updates are not permitted.

Useful indexes:

- `(voter_id, created_at desc)` for recent-exposure filtering.
- Each joke reference for match-history and aggregate rebuild queries.
- A partial index over completed matches for leaderboard aggregation.

Do not permanently prohibit repeated unordered pairs with a unique constraint. An infinite mode may eventually need to reuse a pairing. Avoid repetition through matchmaking history instead.

### `showdown_joke_stats`

Keep the event log as the source of truth, but maintain one aggregate row per joke for inexpensive leaderboards.

Suggested columns:

| Column | Purpose |
| --- | --- |
| `joke_id` | One-to-one reference to the joke. |
| `appearances` | Times issued in a match, including abandoned matches. |
| `wins` / `losses` | Completed overall record. |
| `wins_vs_human` / `losses_vs_human` | Record against human jokes. |
| `wins_vs_ai` / `losses_vs_ai` | Record against AI jokes. |
| `score` | Cached adjusted ranking score. |
| `updated_at` | Last aggregate change. |

Provide a database routine that can rebuild these rows from `showdown_matches`. This makes later formula changes and recovery from aggregation bugs possible.

### Edited-generation lineage

This is not required for the Showdown MVP. When generated drafts become editable, add a nullable reference separate from `source`, for example:

```text
edited_from_generation_id -> generations.id
```

An edited joke remains `source = 'human'` and uses the editor's `author_id`. The lineage field records process history only.

## Server architecture

### Pair creation

Implement pair selection on the server, ideally behind a Postgres function called by a Server Action. The operation should select the jokes, randomize their positions, create the match row, and return its safe public fields.

The pre-vote result must contain only:

- Match ID.
- Left joke ID, setup, and punchline.
- Right joke ID, setup, and punchline.

It must not contain source, author, prompt, model, generation ID, ratings, or Showdown statistics.

Initial eligibility and sampling:

1. Select active text jokes not authored by the voter.
2. Exclude jokes shown to the voter in a recent history window.
3. Prefer two jokes from the same category.
4. Favor jokes with fewer appearances.
5. Draw randomly from the resulting candidate pool.
6. Randomize which joke is left and right.
7. Persist the issued match before returning it.

At the current project scale, this can begin with a simple database query. Avoid making `ORDER BY random()` the permanent high-scale design; move toward exposure-weighted candidate sampling as the corpus grows.

If no unseen pair remains, progressively relax recent-history restrictions rather than presenting an error immediately.

### Vote submission

Add an action with the conceptual interface:

```text
submitShowdownVote(matchId, winnerJokeId)
```

The server must:

1. Authenticate the current user.
2. Validate that the match belongs to that user.
3. Validate that the match has not expired or already been completed.
4. Validate that the proposed winner is one of its two jokes.
5. Recheck that the voter does not own either joke.
6. Complete the match with a conditional update.
7. Update both aggregate rows in the same database transaction.
8. Return the source reveal and, when practical, the next pair.

Use a Postgres function or an equivalent atomic database operation. A separate read followed by an unconditional write would allow double-clicks or concurrent requests to count more than once.

## Blindness and security model

The Showdown client must never receive provenance before voting. Pair selection must not happen from a client-side pool of complete joke rows.

The existing `/jokes` feed exposes provenance, so users may recognize content they have seen before. The MVP promises a blind Showdown interface, not cryptographic secrecy across the whole product.

If stronger blindness becomes necessary later:

- Serve sanitized joke shapes through narrowly scoped database functions or views.
- Revisit the broad authenticated read policy on `jokes`.
- Consider withholding public provenance until a joke has completed its initial Showdown evaluation.

Row-level security must ensure that users cannot inspect or modify another user's match rows. Leaderboard reads should expose aggregates, never voter identities or individual voting histories.

## Ranking

### Joke leaderboard

Use a Wilson lower-bound score for the first release rather than raw win percentage.

This prevents a joke with one lucky win from outranking a joke with hundreds of strong results. Display the adjusted score alongside understandable supporting data:

- Wins and losses.
- Raw win rate.
- Total completed matchups.
- Record against human jokes.
- Record against AI jokes.
- Source and human author, where applicable.

Require a minimum number of completed comparisons, initially 10 to 20, for the primary leaderboard. Put newer jokes in a separate rising or provisional section.

Retaining match events allows a later move to Bradley-Terry, Elo, or Glicko if opponent strength becomes important.

### Human leaderboards

Only jokes with `source = 'human'` and a non-null `author_id` contribute to their author.

Create two views:

1. **Top humans**: adjusted performance of their human jokes against all eligible opponents.
2. **AI slayers**: adjusted performance of their human jokes specifically against AI jokes.

Initial qualification requirements:

- At least 2 to 3 distinct human jokes.
- At least 20 to 30 completed matchups.
- A minimum number of distinct voters.
- No self-votes.

Use an adjusted rate rather than total wins so posting volume alone does not determine rank. Exact thresholds should be configuration constants so they can change as participation grows.

## User interface

### Routes

Add:

- `/showdown` for infinite voting.
- `/showdown/leaderboard` for joke and human rankings.

Add Showdown to the primary site navigation.

### Showdown screen

The screen should include:

- Two equal-size, equally emphasized joke choices.
- Entire cards as accessible buttons.
- A and B labels that do not imply rank.
- Keyboard operation and visible focus states.
- An immediate disabled state after selection.
- A short result state revealing human or AI for both jokes.
- Automatic loading of the next pair.
- Loading, expired-match, insufficient-pool, and recoverable-error states.

Do not show running streaks that encourage thoughtless rapid voting. If lightweight engagement feedback is added, keep the joke comparison as the primary focus.

### Leaderboard screen

Provide three tabs or equivalent filters:

- Best jokes.
- Top humans.
- AI slayers.

Clearly label provisional entries and explain adjusted scoring in plain language.

## Abuse resistance and data quality

Include these protections in the MVP:

- Authentication and completed onboarding required.
- Server-issued match IDs.
- One accepted vote per match.
- Self-authored jokes excluded.
- Recent-pair suppression.
- Vote timestamps retained.
- Basic rate limiting for impossible or automated voting speeds.
- Minimum distinct-voter requirements for leaderboard qualification.

Track suspicious behavior without assuming that unusual taste is abuse. Signals may include extremely short decision times, repeated fixed-position selection, and sustained high-volume voting. Suspicious votes can initially be flagged for analysis rather than automatically deleted.

## Image memes later

Reuse the same match and ranking records. Add separate eligibility pools rather than comparing unlike formats:

- Text versus text.
- Image versus image.

For image Showdown:

- Preload both images before enabling voting.
- Normalize their visible area so dimensions do not create an advantage.
- Prefer similar aspect ratios where practical.
- Keep AI-image provenance separate from file format, as `source` is already separate from `kind`.
- Relax the current AI-must-be-text constraint only after there is a real AI-image generation and storage pipeline.

## Test plan

### Database and actions

- [x] A joke is never paired with itself.
- [x] Only eligible text jokes are selected in the MVP.
- [x] The voter's own jokes are excluded.
- [x] Left and right placement varies.
- [x] Invalid winner IDs are rejected.
- [x] Another user's match cannot be read or completed.
- [x] Concurrent submissions produce one completed vote.
- [x] Completed matches cannot be changed.
- [x] Aggregate rebuilds reproduce the stored totals.
- [ ] AI jokes never credit their prompter on human leaderboards.
- [ ] Edited AI-derived jokes classified as human credit the human editor.

### Interface

- [x] Pre-vote network data contains no source or author information.
- [ ] Mouse, touch, and keyboard voting work.
- [x] Repeated clicks do not create repeated votes.
- [x] The source reveal matches the server result.
- [x] The next pair loads without a full-page navigation.
- [ ] Empty, expired, loading, and database-error states are usable.
- [ ] Mobile and desktop layouts give neither option more visual prominence.

## MVP boundary

The recommended first release includes Phases 1 through 3:

- Secure text-only Showdown voting.
- Infinite pair loading with basic exposure balancing.
- Post-vote source reveals.
- A statistically adjusted best-jokes leaderboard.

Human leaderboards should be implemented next but should not be promoted until enough distinct jokes, voters, and completed matchups exist to make their rankings meaningful.

## Deferred decisions

Resolve these with real usage rather than blocking the MVP:

- Exact recent-history window.
- Exact leaderboard qualification thresholds.
- How long a server-issued match remains valid.
- Whether suspicious votes are excluded automatically or only flagged.
- Whether source reveal should remain immediate if it noticeably biases later votes.
- Whether edited-generation lineage should ever be visible to users.
